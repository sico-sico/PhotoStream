## 技术选型

| 方面 | 选择 | 原因 |
|------|------|------|
| 运行时 | Electron 44（Chromium 152 / Node 24） | 图像处理生态成熟，前端开发效率高 |
| 缩略图 | `sharp`（libvips） | 实测 512px WebP 约 1.2 ms/张，比 `nativeImage.createThumbnailFromPath` 快 5.5 倍、体积小 10 倍 |
| EXIF | `sharp.metadata()` + `exif-reader` | `exif-reader` 零依赖且仍在维护；`exifr` 已 4.5 年未更新 |
| 元数据缓存 | `node:sqlite`（Electron 内置） | 不需要额外原生模块，也不必为几万行数据手写文件格式 |
| 图像尺寸 | `image-size` | 从同一个 512 KB 前缀里拿宽高，EXIF 在这些导出里不含像素尺寸 |
| 画布 | 单容器 CSS `transform` + 视口裁剪 | 见[拖动性能](#拖动性能) |
| 文件监听 | Node 内置 `fs.watch` | 少一个依赖，避开 ESM/CJS 问题；本应用只面向 Windows |
| 打包 | `@electron/packager` | `electron-builder` 会引入 8 个已知漏洞和 4 个弃用包 |
| 类型系统 | TypeScript 7 | 原生 Go 实现，类型检查快一个数量级；迁移只需去掉 `baseUrl` 并显式声明 CSS 导入 |

主进程实际用到三个第三方包，它们被打包的方式不同：

| 包 | 声明位置 | 打包方式 |
|---|---|---|
| `sharp` | `dependencies` | 原生二进制，需要从 `app.asar` 解包（`asar.unpack`） |
| `exif-reader` | `dependencies` | 纯 JS，由 `externalizeDepsPlugin` 外部化后随 `node_modules` 一起进包 |
| `image-size` | `devDependencies` | 纯 JS，体积小且无副作用，被 Vite 直接内联进 `out/main/index.js` |

`image-size` 放在 `devDependencies` 是有意为之：它会被打进 bundle，运行时不需要在 `node_modules` 里找到它。若将来改成外部化，必须同时把它移到 `dependencies`，否则打包后会在启动时 `MODULE_NOT_FOUND`。

选型前的完整实测过程见 [research.md](./research.md)。

### 图片渲染链路

**没有专门的渲染引擎**：没有 Canvas、没有 WebGL、没有 PixiJS/Three.js。图片就是普通的 `<img>` 标签，解码与合成全部交给 Electron 内置的 Chromium。这不是省事，而是约束下的正确选择——整个墙面是几千个 DOM 元素，用视口裁剪把挂载点控制在 600 以内，Chromium 的合成器已经足够；换成 Canvas 就得自己实现文字排版、圆角裁剪、命中测试和滚动条联动，而这些现在都是免费的。

```
原始 JPEG / PNG ──sharp/libvips──▶ WebP 512 / 2560 / viewer<edge> ──┐
                                                                  ├──▶ pic:// ──▶ <img> ──▶ Chromium 解码 ──▶ GPU 合成
原始 JPEG / PNG ─────────────────────────────────────────────────┘
```

| 环节 | 技术 | 说明 |
|---|---|---|
| 解码/合成 | Chromium 152（Blink + Skia） | Skia 负责缩放重采样，默认双线性/三线性，不覆盖 `image-rendering` |
| 元素 | `<img>` | 无 Canvas。`Tile` 带 `decoding="async"`，避免解码阻塞主线程 |
| 缩放/平移 | 墙：CSS `transform: translate3d(...) scale(...)`；查看页：改**布局尺寸** | 墙面用一个容器变换，走合成器、不触发重排；查看页则必须改布局尺寸，原因见[查看页的 1:1 锐度](#查看页的-11-锐度) |
| 合成提示 | 墙：`will-change: transform`；查看页：仅在拖动/双指期间提升图层 | 静止的查看页**不能**带 `will-change: transform`，否则位图会被 GPU 双线性重采样 |
| 像素对齐 | `snapToDevicePixel(value, dpr)` | 150% 显示缩放下 1 CSS px = 1.5 设备像素，比例算出的尺寸几乎必然落在设备像素之间 |
| 预处理 | `sharp`（libvips） | **主进程**执行，渲染进程只拿成品 WebP |
| 传输 | `pic://` 自定义协议 | `registerSchemesAsPrivileged` 里开 `standard/secure/stream`，处理器用 `net.fetch(pathToFileURL(...))` 转发，因此**原图支持 Range 请求**，大 JPEG 可以边下边解码 |

查看器的原图 URL 由主进程按**相对图库根目录的路径**生成，例如 `trip/photo.jpg`，不能只传 basename。递归图库里文件名可能重复；只传 `photo.jpg` 会解析到错误位置或 404，查看器就会一直停留在模糊的预览图。渲染进程通过 `thumbUrl(photo, 'full')` 请求 URL，不接触绝对磁盘路径。

**LOD 是我们自己控制的唯一一环**：`wall` 512px、`zoom` 2560px、`full` 原图，由实际显示尺寸和 DPR 推导（见[小图的 zoom 档位是冗余的](#小图的-zoom-档位是冗余的)）。Chromium 只负责把拿到的位图缩放、合成，不会替我们挑分辨率。

**查看页还会按实际绘制尺寸下单**：`viewerEdge(devicePx)` 把显示所需的设备像素向上对齐到 256 的桶，主进程据此生成 `viewer2048` 这类专属档位。给一张要画在 1841 设备像素上的照片发 2560 的位图，Chromium 会再缩一次，那一次重采样正是「比系统看图器糊」的来源。

**查看页用两层 `<img>` 叠加**：先显示缓存缩略图（`preview`），原图 `onLoad` 后预览层淡出。否则原图解码期间是一片空白。

**为什么不换成 Canvas/WebGL**：DOM 方案在 3226 张、600 挂载点的实测下仍然流畅（见[拖动性能](#拖动性能)）。真正会先撑不住的是布局与 DOM 数量，而不是绘制；那一步真到了再谈迁移才划算。

## 实现细节

改动相关代码前值得先读的部分。

### 拖动性能

3226 张照片时拖动卡顿，逐项测量排除了几个想当然的病因：

| 假设 | 实测 |
|------|------|
| transform 写入太慢 | 0.51 ms/次，不是原因 |
| box-shadow 太多 | 去掉全部阴影后仍 28 ms/帧 |
| 字幕文本重绘 | 隐藏后反而更慢 |
| 视差/布局刷新 | 强制 style+layout 仅 3.6 ms |
| **同时挂载的 DOM 节点数** | **3026 个 → 27 ms/帧；只留 200 个 → 17 ms/帧** |

即使完全不经过 React、直接写 `style.transform` 也只有 26 ms/帧，所以瓶颈是节点数量本身。两个修复：

1. **视口裁剪**（`shared/cull.ts`）：只挂载可见区域加一屏边距的瓦片，上限 600 个。
2. **拖动期间直写 DOM**（`usePanZoom` + `Wall` 的 `applyTransform`）：每帧只改 `style.transform`，松手时提交一次 React 状态。

结果：DOM 瓦片 3226 → 64，帧时间中位数 **17 ms（60 fps）**，p95 17 ms，超时帧 0。

### 支持的格式与日期兜底

格式白名单只有 JPEG 与 PNG。两者的差别不在「能不能读」，而在代价：

| 输入 | 文件（4000×3000） | 生成 512px WebP | 查看页 `full` 档 |
|---|---|---|---|
| JPEG q88 | 2.1 MB | 55 ms | Chromium 直接解 |
| PNG RGB | 24.9 MB | 169 ms | Chromium 直接解 |
| PNG RGBA | 26.4 MB | 258 ms | 同上，但要拍平 |

PNG 是无损的，必须解完所有像素才能缩放，没有 JPEG 的 DCT 部分解码可用，所以慢 3–5 倍、大 12 倍。这不影响正确性：`sharp` 原生支持 PNG，`image-size` 从 IHDR 就能拿到宽高（512 KB 前缀绰绰有余），EXIF 与 ICC 也照常能取。`metadata.db` 与缩略图缓存的逻辑一行都不用改。

**HEIC 仍然不支持，而且不是「缺个依赖」那么简单。** 打包的 libvips 只编入了 AV1 解码（`sharp.format.heif` 只认 `.avif`），对 HEIC 会明确报：

```
heif: Error while loading plugin: Support for this compression format has not
been built in: HEVC (a suitable decoder plugin is libde265)
```

更关键的是第二道坎：查看页的 `full` 档**直接把原图流给 `<img>`**，而桌面版 Chromium 不解 HEVC。也就是说 HEIC 即使能生成缩略图，点开仍然是破图，必须为它额外生成全尺寸位图——那是改架构，不是加扩展名。`sharp` 官方支持列表里也没有 HEIC。

**透明通道一律拍平到白底**（`buildThumbnail` 里的 `.flatten({ background: '#ffffff' })`）。墙面把照片当相纸呈现，保留 alpha 会让背景渐变从照片里透出来，圆角截图看起来像个洞；不透明的 WebP 也更小、解码更快。拍平放在 `resize` **之后**：libvips 对 RGBA 做的是预乘重采样，先拍平会让透明像素里未定义的颜色渗进边缘。JPEG 没有 alpha，这一步对它是 no-op。

查看页的 `full` 档流的是原图，PNG 的 alpha 会保留下来，所以 `.viewer-image` 上有一层 `background: #fff` 兜底——否则透明区域露出来的是深色遮罩，和墙面上看到的不一致。

**日期兜底：EXIF 优先，其次文件修改时间。** 照片的 `dateSource` 现在是 `'exif' | 'mtime' | 'none'`：

- `exif` 是权威值，相机记录的快门时刻。
- `mtime` 是兜底。截图类 PNG 根本没有 EXIF，如果让它们「无日期」，就会被固定排在墙尾，无论实际是什么时候做的。`fileModifiedDate()` 取**本地时区**的日历日，因为用户对照的是自己墙上的时钟。
- `none` 只在连 mtime 都读不出来时出现，实际意味着文件在扫描过程中消失了。

界面会标明这个近似：查看页底栏写成「2019-07-14 (文件日期)」，缩略图 tooltip 同样，EXIF 面板的「File」分组里多一行「日期来源：文件修改时间」。不标出来才是问题——复制一次文件夹就会改掉所有这类照片的「拍摄日期」，把它当作事实展示是一种安静的欺骗。

缓存里只存 EXIF 的原始结论（`takenAt`），兜底在构造 `Photo` 时计算。这样换策略不会留下过期的派生日期，而缓存键本来就带 `mtime`，两者不会错位。

### 查看页的 1:1 锐度

单张查看页曾长期比 Windows 自带的照片查看器糊，在 4K 屏、150% 显示缩放下还带明显锯齿。一条条排除后，最终定位到**三个叠加的原因，全都出在我们这边**，与 Chromium 的图像解码能力无关。

测量方法：打开一张 8064×6048 的原片，滚到 1:1 上限，截取舞台中央 500×340 的一块，与原片同一区域的像素比对。指标是**梯度能量**（相邻像素差的均方根），越高越锐；参考值是原片同一区域用 Lanczos 缩放到位图实际绘制尺寸的结果。

| 版本 | 梯度能量 | 相对原片 |
|------|---------|---------|
| 原片参考 | 19.41 | 100% |
| ① 原图 + `transform: scale()` + `will-change` | 16.66 | 86% |
| ② 去掉静止时的 `will-change` | 18.14 | 93% |
| ③ **再改成布局尺寸 + 设备像素对齐（现状）** | **18.96** | **98%** |

三个原因分别是：

1. **`will-change: transform` 把照片提升成独立合成层。** 提升后的图层只光栅化一次，之后的缩放交给 GPU，而 GPU 只会双线性插值——既糊又出锯齿。修复是只在**手势进行时**提升（`.viewer-stage.dragging` / `.pinching` / `.zooming`），静止时撤掉。滚轮缩放没有抬起事件，所以用 `zooming` 类保持 220 ms 后自动释放。
2. **`transform: scale()` 本身就够损失锐度。** 即使没有 `will-change`，被放大的 `<img>` 仍是先按布局尺寸光栅化、再交给合成器放大。改成把放大后的尺寸直接写进 `width`/`height`，`transform` 只负责位移。这是最反直觉的一条：`scale()` 常被当作「不影响清晰度」的廉价变换，实际对图片并不成立。
3. **绘制矩形没落在设备像素网格上。** 150% 缩放下 1 CSS px = 1.5 设备像素，按比例算出来的 1227.385 CSS px 等于 1841.078 设备像素——差 0.078 就够 Chromium 把整幅图重采样一遍。`snapToDevicePixel(value, dpr)` 把所有几何值（布局尺寸、位移）对齐到 `1/dpr` 的网格。

对齐的细节：元素是网格居中项，绘制左边缘实际在 `(viewport - painted) / 2 + x`，所以必须对齐**这个表达式**再反解出 `x`（`imageStyle` 里的 `offset`），直接对齐 `x` 无效。此外 `painted` 的尺寸与 `fitScale` 之间存在浮点尘埃，`translate` 里出现 `-1.4e-14` 这类值时 CSS 会整条丢弃变换——因此输出前统一 `toFixed(9)`。

配套改动：舞台的网格必须固定成 `grid-template-columns: 100%; grid-template-rows: 100%`。一旦照片按放大后的尺寸参与布局，`auto` 列会被撑到照片的 max-content 宽度，照片随即贴到左边、所有平移边界随之失效。

**为什么没有引第三方库**：编码质量不是瓶颈（同帧对比 q82 与无损几乎无差），Lanczos 也不缺（`sharp` 默认就用 lanczos3）。真正缺的是让位图尺寸、绘制尺寸和屏幕像素三者重合，这件事不需要额外依赖。

回归防线分三层：`snapToDevicePixel` 的单元测试（含「偏移不超过半个设备像素」的不变量）、查看器测试断言 `transform` 里不出现 `scale(` 且绘制尺寸落在网格上、样式表读取测试禁止 `.viewer-image` 携带 `will-change`。

### 滚动条预取

竖向滚动条暴露出视口裁剪的另一个失效场景：滚动条可以一步跳过几万像素，而缩略图是按**当前视口**请求的，于是跳转落地后满屏都是占位图。

修复在 `shared/cull.ts` 的 `prefetchIdsForScroll`：按**目标位置**（而不是当前位置）算出前后各一屏的区间，提前发起请求，跳转动画播放期间缩略图就已经在路上了。区间按缩放换算，保证任何缩放级别下都覆盖同样多的屏幕内容。

**实测推翻的第一版设计。** 最初的实现一次预取整个区间（数百张），结果跳转后 15 秒仍有 14/81 张可见瓦片是空白——因为主进程只有 4 个编码槽，预取把**已经在屏幕上的**瓦片挤到了队尾。改法有两处：

1. 预取批量收到 80 张（约一屏），并延后 120 ms 发起，让当前视口先赢；
2. 主进程的编码队列改为**双通道**（`interactive` / `background`），预取走后者，永远排在可见瓦片之后。

另外，滚动条拖动会连续发出大量指针事件，所以目标值先落到 state 再由 effect 合并——每个不同的目标只发一次批量请求，而不是每个像素发一次。

### 拖入 / 命令行打开

两个入口最终走同一条路径，避免行为漂移：

1. **拖入**：`useFileDrop` 从 `File` 取回真实路径（Electron 32 起 `File.path` 已移除，必须用 `webUtils.getPathForFile`），再调 `openDropped`。
2. **命令行**：`photoFromArgv` 从 `process.argv` 里挑出第一个 JPEG；主进程通过 `photos:openExternal` 通知转发给渲染层。

主进程的 `resolveOpenTarget` 统一判定：目录就开目录，JPEG 文件就开它所在的目录并返回该文件路径。渲染层拿到后聚焦这张照片并展开 EXIF 面板。

两个坑：

- **单实例**：每次「打开方式」都会起新进程，所以加了 `requestSingleInstanceLock`，第二个实例把参数转交给第一个后退出。

### EXIF 面板：一个被记住的偏好

`viewerInfo` 描述的是**用户想怎么看图**，不是某张照片的属性，所以它跨照片、跨关闭重开、跨重启都保持。

早期实现把它当成「单张照片」的意图：点击瓦片或 `←/→` 翻页时清除。结果是用户按下 `I` 打开面板，翻到下一张就自己关掉——看起来像功能坏了。现在：

- 点瓦片、翻页、关闭再打开查看器都不会改变它；
- 按 `I`、点工具栏按钮、点面板自己的关闭按钮都会把选择写回 `wallReducer`，并入 `Settings` 持久化（`settings.json` 的 `viewerInfo`）；
- 只有「从外部打开某一张照片」（拖入单个文件、资源管理器「打开方式」）会把它**置为 true**，因为此时文件详情正是用户所问；它从不会主动置为 false。

控件是受控的：`Viewer` 只接收 `infoOpen` 并通过 `onInfoOpenChange` 上报，状态归属墙，否则偏好无法持久化。

### 随机播放

一个**观看模式**，不是第二种布局：在当前的筛选结果上铺一张居中照片和一圈漂浮的小图，用来漫无目的地浏览，而不是定位。

进入时切换到系统全屏，退出时还原。状态放在 `App`，因为它是「同一批照片的另一种呈现」，不属于 `useWall`。

**状态机**（`renderer/state/randomShow.ts`）是纯函数，`advance(state, { now, photoMs, batchMs })` 把时钟作为参数传入，所以节拍规则可以不用等待就测完：

| 规则 | 值 | 说明 |
|---|---|---|
| 自动提升 | 8 s | 环里停留最久的那张升为中央 |
| 换一批 | 60 s | 整个环换新；与提升同时到期时**换批优先** |
| 悬停暂停 | — | 指针停在小图上时两个计时都停 |

**换批时旧环整批从窗口下方掉落**（`state.falling`）。提升只是环内换位，用位移过渡即可；换批则是整批作废，九十张一起消失会读成渲染故障，所以要让它们**一起掉出去**，读成「这一批结束了、下一批发牌」。

- 掉落卡片带着**离开时那个 box 和那套姿态**，所以第一帧不发生跳变，是从它原来站的位置开始掉。
- 三层同时变化：加速下落（`140vh`，比窗口高，保证任何一张都彻底离开）、`rotateX` 增大 46°（面朝下翻出去而不是平板下滑）、绕自身轴旋转（方向由该张自己的倾角符号决定，避免整排同向转）。
- 错峰最多 ~170ms（按坐标取模），一起掉但不整齐，这是「一摞照片」和「一块幕布」的区别。
- 落下时 `z-index: 2`：盖在新环（1）之上、中央照片（4）之下——旧批次从新照片前面掠过，但永不越过主体。
- 组件在 `FALL_DURATION_MS`（1150ms）后发 `show/clearFalling`。不清会每次换批留一堆已解码图片在后台，90 张的量级就是整个随机播放的内存大头。清理带 `fallingKey` 校验，新一次掉落不会被上一次的定时器提前掐断。
- `prefers-reduced-motion` 下直接 `display: none`：掉落没有「温和版本」，静止的一帧只是屏底堆了一排照片。

**界面上没有进度。** 左上角曾有一个 `{shown} of {total}` 计数，指的是「此刻屏幕上有几张 / 图库共几张」。它被删掉了：随机播放没有顺序也没有终点，那个数字既不会递增也不表示还剩多少，用「第 N 张」的措辞读起来却像是在走一个有终点的队列。现在顶部只保留「已暂停」提示和退出按钮。

**进入时只发一次牌。** 这条约束比看起来重要，因为「重新发牌」是可见事件：屏幕上每一张照片都会换掉。

组件用 `ResizeObserver` 量窗口，而 `observe()` 之后浏览器**必定投递一次初始通知**，所以挂载时会量两次。早期实现把结果无条件写进 `setViewport({ width, height })`：数值没变，但对象引用变了，于是启动 effect 重跑、`show/start` 又抽一次中央照片、整圈重发。表现是每次进入随机播放都闪一下，窗口还在稳定时（动画、任务栏、身后墙面的滚动条出现）会连续几次，读起来就是「疯狂刷新」。

两处修复缺一不可：

- `measure` 里比较四舍五入后的宽高，相同就返回原对象。**引用稳定**才是 effect 不重跑的前提。
- 启动 effect 用 `started` ref 守住，只有第一次通过。依赖数组里同时有 `pool` 和 `viewport`，而它又要等窗口量好、池子非空，所以合法地会跑多次——但只有一次能发牌。

`pool` 变化（文件监听、重新扫描、筛选）走 `show/pool`，只更新候选池、不动屏幕，留给下一次换批。早期实现让它参与重发牌，于是照片库后台刷新一次，正在看的一圈就整批换掉。

实测（300 张图库、8 秒采样）：修复前 4 秒内环的张数从 39 变到 38，说明发生了重发牌；修复后 8 秒内环的张数**一次都没变**，唯一的中央变化发生在 8 秒调度点。回归测试用会真正投递通知的 `ResizeObserver` 替身复现初始投递，断言中央与整圈 id 都不变——去掉任一修复后该测试失败。

**选照片后的行为**：被点/被提升的照片入中央，**原中央照片退场**，从池中抽一张不在屏上的照片填进它留下的格子。早期版本把原中央留在环里，屏幕于是慢慢积累「今天已经看过的」，与随机播放的目的相反。

**池子耗尽时怎么办**，两条规则：

1. **环大小 ≥ 图库张数时不再换批**（`turnoverAddsPhotos`）。此时每张照片都已经是候选，换批除了把整圈摔出窗口再发回来之外什么也没做——代价是完整的掉落动画，收益为零。跳过换批后提升照常进行，屏幕仍在变，只是从「重新洗牌」变成「持续轮转」。

2. **抽取分两轮：先取没上过屏的，不够再补齐。** 这是必须的，因为换批的抽取本来排除整个当前屏幕：

   图库 30 张、默认环 70 时，第一轮可用数为 0，环于是只剩 1 张。实测（每秒推进时钟，采样 5 分钟）：

   ```
   修复前  30 张 / 环 70 -> 29 → 28 → 1 → 28 → 1   （每分钟塌一次）
   修复后  30 张 / 环 70 -> 29 恒定，照片持续轮转
   ```

   补齐时只排除中心照片，保证同一张不会既在中心又在环上；回归测试逐秒断言屏幕上从不出现重复 id。

`focusPhoto` 也补了同样的第二层兜底，但对象不同：第一轮仍排除全部屏上照片，抽不到时**只把即将退场的原中央照片放回来**。这一步是为规则 1 服务的——禁用换批之后，三张照片的图库若沿用「抽不到就留空」，会缩到 1 张然后永久卡死。放回即将离场的照片不会造成重复（它已经不在屏上了），三张照片于是能一直轮转。

**`surrounding` 是队列，`boxes` 是布局，两者顺序不同**。`surrounding[0]` 被定义为「停留最久、下一个被提升」的那张；`boxes` 保留各自的坐标，好让替补照片出现在被提升者腾出的那个格子里，环因此不重排。所以 `focusPhoto` 里替补照片**追加到 `surrounding` 末尾**，但**接管被提升者的 box**。

早期版本把替补写在被提升者的原索引上，两件事共用一个数组顺序。后果是：替补一插进来就成了 `surrounding[0]`，8 秒后它自己被提升，它的替补又占住 `surrounding[0]`——**同一个格子**无限循环，环上其余照片一次也不会被提升。症状是「每次替换的都是同一个位置」，但照片本身确实在变（每次都随机抽新的），所以只断言 id 抓不到，必须断言**格子坐标**。回归测试覆盖了坐标不重复、替补在队尾、连续提升不重样三点，且在还原修复后确认三条全部失败。

**布局**（`shared/random.ts`）：

- 中心照片占窗口短边的 **68%**（`CENTRE_FRACTION`），按 contain 计算，所以竖图受高度限制。
- 环上每张按 `size² = 面积` 取尺寸，与长宽比无关，避免竖向图在视觉上更有分量。
- **允许有界重叠**：一张照片被邻居遮住的累计面积上限为 25%。按累计而非逐对计算——被四张各遮 20% 在视觉上就是被遮了大半。中央照片**从不被遮挡**。
- 每张有独立的静止倾角、3D 朝向、浮动周期与相位。

**环的容量是「候选数」，不是「显示数」**。`ringSize` 设置（齿轮菜单里的滑杆，30–90，默认 70）决定向散点布局提交多少个候选，`scatterAround` 再丢掉放不下的。2560×1440 下的实测：

| 候选数 | 实际放下 | 环占屏面积 |
|---|---|---|
| 30 | 30 | 0.216 |
| 60 | 52 | 0.337 |
| 90 | 63 | 0.390 |

所以 90 已经是这台机器能放下的上限附近，再往上加没有效果；调小的方向才是有用的，因为候选少意味着间隙大、画面更静。范围下限取 30：再少就不再像一个环绕中央的「云」。

设置改动会**立刻重新铺设环**（`show/ringSize`），不等下一次换批——否则滑杆拖到 30 和 90 看起来完全一样，要等一分钟才见分晓。重铺时中央照片不动，已在屏上的照片都保留（只增删卡片，不换一批），所以拖动滑杆不会让画面闪。越界值由 `clampRingSize` 夹住；`sanitizeSettings` 只在值是有限数字时才交给它，因为 `Number(null)` 是 0，会被夹到下限、把环悄悄砍到 30。

**3D 是真的几何**，不是阴影错觉：容器一个 `perspective: 1400px`，每张照片带自己的 `rotateX`/`rotateY` 和负 `translateZ`，所以远边确实更短、远处照片确实更靠后；`soft-light` 光泽层跟随倾角，卡片转动时光会掠过表面。远照片的倾角更大，整体正负平衡，画面不会歪。

实测（`matrix3d` 判定）：60 张同屏时 **60/60 都计算为非平面矩阵**，倾角取值 60 种互不相同。

**照片是有厚度的实物，不是薄片**：

- 图不是卡片本身，而是**印在卡纸上的**：卡片留 3px 相纸白边（中央大图 7px），底衬是 160° 的浅色渐变（上偏亮、下偏灰），所以边缘会随倾角吃到不同的光。
- 侧壁用两条**零模糊的实色 `box-shadow`**（`1px 2px` 与 `2px 3px`）画出来，是纸芯的灰褐色。卡片的倾角越大，露出的侧壁越宽，和真拿在手里一样。
- 侧壁**不能用** Z 轴偏移的伪元素实现。`filter` 与 `opacity` 都是分组属性，任意一个都会把 `transform-style` 强制降级成 `flat`；被压平的 `::before` 会变成普通定位元素，画在 `<img>` **上面**——卡片于是只剩一个灰色空框。这个 bug 实际发生过，现在由单元测试（禁止 `.random-show-thumb::before`）与端到端测试（`elementFromPoint` 必须命中图片本身、`naturalWidth > 0`）双重看守。

**悬停是「靠近」，不是「扶正」**：

- 指针进入时不改姿态，只放大 8%、提亮、去模糊。扶正会让卡片轮廓在指针下移动，指针一旦落到轮廓之外悬停就丢失，卡片弹回又再次触发——重叠时看到的**抖动**就是这个。
- 放大用独立的 `scale` 属性而不是重写 `transform`：运行中的动画优先级高于 `transform` 声明，写在 `transform` 里会被静默忽略。
- 浮动动画用 `animation-play-state: paused`，而不是 `animation: none`。`none` 会把卡片瞬移回静止姿态、轮廓从指针下跑掉；`paused` 则停在动画当时的位置。顺带解决了「照片一直在动，点下去可能点到邻居」的问题。

`prefers-reduced-motion` 下关闭全部漂动与光泽，保留姿态与布局。

**分辨率按实际显示尺寸选档**，而不是固定一档。中央照片要占窗口短边的 68%，所需像素随窗口和屏幕 DPR 变化：

| 窗口 | 需要显示 | 档位 |
|---|---|---|
| 1440px @1x | 979px | `zoom` |
| 2160px @1x | 1469px | `zoom` |
| 2160px @2x | 1469px | **`full`** |
| 2880px @2x | 1958px | **`full`** |

早期版本对中心也复用墙面的 `wall` 档（512px）。因为 `max-width: 100%` **从不放大**，一张 340×512 的图放在 661×994 的框里只渲染成 339×513——看起来「居中照片怎么这么小」正是这个原因，实测填充率 51%。现在用 `centreThumbLevel()` 复用既有的 `pickThumbLevel`，由窗口尺寸与 DPR 推导；窗口在显示器间拖动导致 DPR 变化时也会重新判定。修复后同一框内渲染为 659×995，填充率 100%。

环上小图仍用 `wall` 档：它们屏幕上很小，给 60 张请求高清会解码几十兆像素而无可感收益。`urlMapsByLevel` 因此按档位分别导出映射，而不是合并进 `thumbUrls`——墙面必须继续用它自己缩放所要求的档位。

### 递归扫描

开启子文件夹后会递归遍历，三个约束：

- 用 `realpath` 记录已访问目录，避免 junction/symlink 成环；另有 `MAX_SCAN_DEPTH = 24` 作为兜底。
- 跳过 `.` 开头的目录和 `node_modules`、`$RECYCLE.BIN` 一类目录。
- 返回的 `name` 是**相对路径**（`2024/a.jpg`），否则不同子目录里的同名文件会互相覆盖。

监听器本身始终是递归的，但关闭该选项时会过滤掉子目录事件——否则扫描结果和实时更新会不一致。

### 打开文件夹时的磁盘 I/O 与 Defender

应用**从不**启动子进程（代码里没有 `child_process`、`spawn`、`exec`），也不会主动调用任何杀毒软件。打开文件夹时 Defender 活动上升，是因为它作为文件系统过滤驱动挂了「实时保护」，**我们读的每个文件都要经过它扫描**。这是 Windows 的固有行为，不是应用的问题。

扫描阶段的 I/O 量来自 EXIF 前缀读取：每张照片读 512 KB。3226 张的库因此约读取 **1.6 GB**（库本身 42.5 GB）。512 KB 这个值有实测依据：64 KB 会漏掉 151 张（EXIF 段落在其后），而整轮解析约 1.1 ms/张。

实测（`scripts/diagnose-defender-load.mjs`，每 200ms 采样 `MsMpEng` 的 CPU）：

| 库 | 张数 | 扫描耗时 | Defender 峰值 CPU | Defender 平均 | 对照（explorer） |
|---|---|---|---|---|---|
| Cosplay | 309 | 209 ms | **34%** | 11.3% | 0% |
| Export | 3226 | 1671 ms | **28%** | 8.3% | 0% |

对照组 `explorer.exe` 全程 0%，说明上升确实来自文件扫描而非采样噪声。

缓存命中后几乎不读文件，I/O 与 Defender 活动都会消失——这也是把 `retain` 的作用域限制在当前目录的原因之一（见上文元数据缓存）。

若要进一步降低影响，可行的方向是缩小前缀读取（需要重新实测命中率），或提示用户把照片目录加入 Defender 排除列表；后者需要管理员权限，且会降低安全性，因此只作为文档建议，不在应用内代做。

### EXIF 时区

`exif-reader` 把拍摄时间当作 UTC 构造 `Date`。必须用 `getUTC*` 读取，用本地时间访问器会让日期偏移一天。已用 3226 张真实照片验证：`getUTC*` 全部正确，本地访问器全部错误。

### 元数据缓存的作用域

`MetadataCache` 用一张 SQLite 表服务用户打开过的**所有**文件夹，所以清理时必须限定范围。

早期实现是 `DELETE FROM photo_metadata WHERE path NOT IN (...)`，只传当前扫描到的路径。后果是**打开另一个文件夹会删光前一个文件夹的全部缓存行**——而「最近文件夹」菜单的全部意义就是来回切换。实测（`Export` 3226 张 / `Cosplay` 309 张）：

| 操作 | 修复前 | 修复后 |
|---|---|---|
| 首次打开 Export | 3960 ms | 3960 ms |
| 切到 Cosplay，再回 Export | **1387 ms** | **107 ms** |
| 再次切到 Cosplay | 141 ms | **10 ms** |

`retain(dir, paths)` 现在只处理 `dir` 下的行。两个 LIKE 前缀分别对应 `/` 和 `\`（数据库里是 Windows 路径，测试里是 POSIX 风格）；转义字符用 `!` 而不是 `\`，因为后者既是路径分隔符又是 SQL 的默认转义符。

### 缩小的下限由内容决定

滚轮能缩到多小不是风格问题，而是几何约束。缩放系数 `s` 下，墙面覆盖 `墙面积 × s²` 个屏幕像素；一旦小于窗口面积，**任何布局都填不满**，`clampWallTransform` 会把墙居中，表现为一条细带漂在空白里。3226 张时该下限是 `sqrt(窗口面积 / 墙面积) ≈ 0.0826`，而滚轮允许到 0.05。

叠加的第二个约束是挂载上限：渲染层最多挂 `MAX_MOUNTED_TILES = 600` 个瓦片，超出的直接被丢弃——也就是「缩小后有些照片不显示」。两者叠加后，只有下限抬高到 **0.3118** 才既不丢图也不留白。

`minScaleForTiles` 用二分法对真实布局求解，而非一个公式：可见瓦片数随缩放**不是平滑函数**，因为布局会按整列/整行重排。注意必须用与挂载**相同的 margin**（`CULL_MARGIN`）测量，否则会少算约三分之一，下限压低后上限依然被突破。

还有一个更隐蔽的坑：缩略图**请求集合**曾与**挂载集合**用了两套规则（一个用 `max(宽,高)` 作 margin 并按布局顺序，另一个用 900px 固定 margin 并按中心距离截断）。两者几乎不重叠，导致挂载的 600 个瓦片**全部无图**。现在两者都来自 `useWall` 里同一次 `cullItems` 调用，由构造保证一致。

### 小图的 zoom 档位是冗余的

`buildThumbnail` 用 `withoutEnlargement`，所以原图小于 512px 时，`wall` 和 `zoom` 两档会编码出**同样的像素**，只是 WebP 质量不同。实测 300×200 的 JPEG：`wall` 200 B、`zoom` 192 B——两次编码、两个文件、一份信息。

`zoomTierAddsDetail(width, height)` 判定长边是否超过 `wall` 档位，`effectiveLevel` 据此把这类照片的 `zoom` 请求重定向到 `wall` 文件。尺寸来自扫描时已解析的 `photo.width/height`，不需要额外读文件。尺寸未知时保守保留独立文件：多一个文件只费磁盘，少一个会让瓦片永远模糊。

### 缩略图缓存分片

一个缓存目录服务用户打开过的**所有**文件夹，每张照片最多 3 个档位（`wall`、`zoom`，以及查看页按实际绘制尺寸下单的 `viewer<edge>`），所以文件数增长比照片数更快。扁平目录在 3 千个文件时还好，到十万级时枚举、删除和资源管理器都会变慢。

缓存键因此是分层的相对路径（`shared/thumbs.ts` 的 `thumbKey`）：

```
thumbs/a/b/<16位hash>-wall.webp
thumbs/a/b/<16位hash>-viewer2048.webp
```

- `viewer<edge>` 的 `edge` 只会是 256 的倍数（`VIEWER_EDGE_BUCKET`），所以窗口尺寸变化不会让缓存无限增长；源图小于 `wall` 档位时这类请求直接复用 `wall` 文件，不额外编码。

- **两级、每级 1 个十六进制字符**，共 256 个叶子目录。分片取自哈希本身，所以同一张照片永远落在同一个目录，查找仍是 O(1)。
- `thumbKey` 返回**相对路径**（用 `/`），调用方负责建目录和拼 URL。
- `pic://thumb` 的 URL 要**逐段编码**。整体 `encodeURIComponent` 会把分隔符变成 `%2F`，得到一个浏览器视为单一不透明段的 URL；解码端也必须逐段解码，否则 `%2F` 会在切分之后才变成分隔符——那正是路径穿越防护最不该有的歧义。

这个结构与 Lightroom 的 `.lrdata` 一致（16 个一级目录 + 十六进制二级目录）。实测 83 个缓存文件摊在 69 个叶子目录里，每个最多 3 个。

没有照搬 LR 的部分：它用**内容指纹**做键（照片改名后预览仍命中），因为它维护的是可任意重排的目录库；我们的键是 `路径+mtime+size`，照片改名就重算，更简单也不会错。它还把 JPEG 内嵌进 `root-pixels.db` 以便原图离线时仍能预览——我们不需要，但代价是数据库从 0.8 MB 涨到百 MB 级。

### 滚轮手势

裸滚轮平移、`Ctrl`（macOS 上是 `Cmd`）+ 滚轮缩放。原来反过来：裸滚轮直接缩放，`ctrlKey` 根本没读。

改的原因是习惯：浏览器、图片查看器、地图都是「滚轮滚动页面」，用户第一次尝试的动作是往下滚，结果改变了缩放而不是沿着图库移动。

两个细节：

- Windows 的 Chrome/Firefox 把触控板捏合合成为 `ctrlKey: true` 的 wheel 事件，所以这个判断顺带让触控板捏合可用，不需要单独的识别器。
- 必须 `preventDefault`：Chromium 会把 Ctrl+滚轮当成**页面缩放**，不拦住的话整个界面会跟着变大。

`shared/wheel.ts` 把判断和位移量算成纯函数（`wheelIntent` / `wheelPan`），所以不用起 Electron 就能测。`deltaMode` 也在这里归一化——鼠标报像素、部分驱动报行/页。

**每个滚轮刻度要有缓动。** 鼠标一格是 100–120 px，而事件本身是离散的：直接赋给 `transform` 会让墙面一次跳一整行，用户的原话是「没有动画效果滑动到目标位置，而是类似直接设定到某个值」。原生滚动对每一格都有缓动，我们照做：`.world.wheeling` 上挂 `transition: transform 0.1s linear`，类名在最后一次滚轮后保留 180 ms。

实测一格 120 px 的绘制位置（每帧采样 `getComputedStyle` 的矩阵）：

```
修复前  0 → -120                     （一帧到位）
修复后  0 → -20 → -40 → -60 → -80 → -100 → -120
```

三个不能省的细节：

1. **只缓动「画」**。`transform` 状态仍然立即提交，所以裁剪集合和缩略图请求跟着真实目标走——这一点是上一版写反的（滚轮期间完全停止发请求），结果整段滚动 `thumbReady` 为 0、满屏空白，落地反而更慢。
2. **线性、不用减速曲线**。`.settling` 的 `cubic-bezier` 每来一格就重起，会变成一顿一顿的脉冲；线性重起才是匀速滚动。时长也必须短（100 ms），否则连续滚动时墙面会明显追不上滚轮。
3. **类名不能提前撤**。transition 是 100 ms，类名保留 180 ms；中途去掉 `transition` 会把剩余距离瞬间跳完，正好是这次要消除的跳格。

拖动与 `Ctrl` + 滚轮缩放**不缓动**：前者的锚点是光标，后者要跟随指针，加了缓动只会让人手延迟。`Wall` 的 `wheeling` 与 `settling` 两个类因此分开，且 `.wheeling` 写在 `.settling` 之前，让程序化移动（键盘、滚动条）保留自己的 220 ms 曲线。

单张查看页保持裸滚轮缩放：那里没有可滚动的内容，滚轮只有一个合理含义。

### 文件锁

libvips 会缓存解码结果并持有源文件句柄，导致用户在 Lightroom 里重新导出同名照片时写入失败。`thumbnails.ts` 调用 `sharp.cache(false)` 解决，并有回归测试守护。

### 设置文件 BOM

Windows 编辑器（记事本、PowerShell）会在 UTF-8 文件前加 BOM，`JSON.parse` 会拒绝。`settings-store.ts` 在解析前剥离，否则用户手改配置文件后所有设置会被静默重置。

### 持久化时序

`useWall` 必须等设置读取完成后才允许写盘。React 的 effect 按声明顺序执行，用 ref 做守卫会在首次渲染时就通过，导致默认值覆盖用户配置。

### 工具栏样式失效

`.history-caret` 规则块漏了闭合括号，导致其后所有 CSS 规则被丢弃——表现为「整个工具栏的按钮都变丑了」。这不是审美问题，是解析失败。修改 `styles.css` 后建议先做一次括号平衡检查。

## 添加语言

英文目录是唯一的来源，它定义在 `src/shared/i18n/messages.ts` 里，`Catalog` 类型由它推导——所以**漏译会在编译期报错**。

1. 新建 `src/shared/i18n/locales/de.ts`：

```ts
import type { Catalog } from '../messages'

export const de: Catalog = {
  // 复制 messages.ts 里 en 的键并填入译文
}
```

2. 在 `src/shared/i18n/locales/index.ts` 中登记（同时记得在 `package.mjs` 的 `KEPT_LOCALES` 里加上对应的 Chromium 语言包，否则文件对话框等系统界面仍是英文）：

```ts
import { de } from './de'

export const BUILTIN_LOCALES: readonly LocaleDefinition[] = [
  // ...
  { id: 'de', label: 'Deutsch', catalog: de }
]
```

第三方也可在运行时注入，无需改源码：

```ts
import { locales } from '@shared/i18n'
locales.register({ id: 'de', label: 'Deutsch', catalog: de })
```
